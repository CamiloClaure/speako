You are a QA engineer. You are given a set of behaviours that are claimed to work.
Your job is to find out whether they actually do.

**You must not edit, create or delete any file in this repository.** You are testing, not fixing.
If something fails, report the failure. Do not repair it.

There is no browser and no Playwright on this machine, so you cannot click through the app.
Test what you can mechanically, and for anything you genuinely cannot verify, write
`NOT VERIFIABLE` rather than guessing. A confident guess is worse than an admission.

## Background you need

Speako is an English-lessons platform used by two kinds of person:

- **students**, who buy lesson packs, book lessons, download materials, and live under `/painel/*`;
- **the teacher**, who manages her calendar, lessons, products and sales, and lives under `/admin/*`.

A teacher has no credits and cannot buy lessons, so no student screen should ever be reachable by her.

People must be able to sign in three ways: a Google button, an email + password form, and a
one-time link sent by email. The link is also the password-recovery path - there is deliberately no
"forgot password" flow.

## Expected behaviours

**A. The web app compiles with no type errors.**
`npm run lint` → exit 0, no output. Quote any error in full.

**B. The web app builds.**
`npm run build` → exit 0, produces files under `web/dist/`. Report the built JS size.

**C. Every endpoint the sign-in screen depends on exists on the API.**
Against `http://localhost:8095/api/v1`, confirm each of these responds with something other than
404 (the status may be 4xx - you are testing that the route is *wired*, not that the credentials work):

| Method | Path | Body |
|---|---|---|
| POST | `/auth/login` | `{"email":"a@b.com","password":"x"}` |
| POST | `/auth/register` | `{"email":"a@b.com","name":"A","password":"senha-forte-1"}` |
| POST | `/auth/google` | `{"id_token":"x"}` |
| POST | `/auth/magic-link` | `{"email":"a@b.com"}` |
| POST | `/auth/magic-link/verify` | `{"token":"x"}` |

Any 404 here means the UI has a button wired to a route that does not exist. Report which.

**D. A student registered through the API lands in a working member area.**
```
POST /auth/register {"email":"qa-fe@speako.com.br","name":"QA","password":"senha-forte-1"}
```
Save the cookie, then with it: `GET /me` → 200 with `"role":"student"`, and
`GET /me/credits` → 200.

**E. The teacher cannot reach student data.**
Obtain a teacher session for `professora@speako.com.br` (set a password with the CLI, or use the
CLI's sign-in-link command, whichever the tool offers). With that cookie:
`GET /me` → 200 with `"role":"teacher"`, and `GET /me/credits` → **403**.

This is the API half of the rule the interface is supposed to reflect. If `/me/credits` returns 200
for a teacher, the interface cannot be trusted to hide it either.

**F. Static inspection of the built bundle.**
Search the built output in `web/dist/assets/*.js` for the Portuguese strings the sign-in screen
should contain. Report which of these appear:
- something offering a password sign-in (e.g. `Senha`)
- something offering account creation (e.g. `Criar conta`)
- something offering the email-link path (e.g. `link`)

This is weak evidence and you should label it as such - it proves the strings were compiled in, not
that they render or work.

**G. Route inventory.**
List every route path the application declares, and mark each one as student area (`/painel/*`),
teacher area (`/admin/*`), or public. Report the list. Do not judge whether the guards are correct -
just report what routes exist.
