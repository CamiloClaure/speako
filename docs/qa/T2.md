# QA: role separation on the Speako API

You are a QA engineer. You are given a set of behaviours that are claimed to work.
Your job is to find out whether they actually do.

**You must not edit, create or delete any file in this repository.** You are testing, not fixing.
If something fails, report the failure. Do not repair it.

## Background you need

Speako has two kinds of account:

- a **student**, who buys lesson packs and books lessons with the teacher;
- the **teacher**, who owns the calendar those lessons are booked into.

A teacher must never be able to buy a pack or book a lesson. If she books a slot in her own calendar
she removes it from the students who could have booked it and spends a credit she cannot own.
The API is expected to refuse, on its own, regardless of what any user interface does or does not show.

## Expected behaviours

For each endpoint, record the HTTP status and the `error.code` from the body for all three callers.

**A. Student-only endpoints refuse the teacher with 403 `forbidden`.**

| Method | Path |
|---|---|
| GET | `/me/credits` |
| GET | `/me/bookings` |
| GET | `/me/orders` |
| GET | `/me/materials` |
| POST | `/checkout` body `{"product_slug":"pacote-4-aulas","quantity":1}` |
| POST | `/bookings` body `{"starts_at":"2026-09-01T12:00:00Z"}` |
| DELETE | `/bookings/qualquer-id` |

Every row, with the **teacher** cookie → HTTP **403**, error code `forbidden`.

**B. The same endpoints still work for a student.**
Every row above, with the **student** cookie → **not** 403. (200, 404, 422 or a domain error are all
fine here - the point is only that the student is not blocked by the role gate.) A student getting
403 anywhere is a FAIL: the gate has been applied in the wrong direction.

**C. Anonymous is still 401, not 403.**
Every row above with **no cookie at all** → HTTP **401**, error code `unauthenticated`.
"Nobody is signed in" and "you are signed in but this is not for you" must remain distinguishable.
Any row returning 403 for an anonymous caller is a FAIL.

**D. `GET /me` works for both roles.**
`GET /me` with the teacher cookie → 200. With the student cookie → 200.
Both accounts need to be able to see who they are; this endpoint must NOT be role-gated.

**E. The teacher's own admin endpoints still work.**
With the teacher cookie: `GET /admin/availability` → 200, `GET /admin/bookings` → 200,
`GET /admin/orders` → 200.
With the student cookie: the same three → 403 `forbidden`.
This proves the new gate did not break the gate that already existed.
